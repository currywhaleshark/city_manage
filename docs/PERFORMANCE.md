# 화면 품질과 성능 측정

## 통합 도시 로딩과 실행 개선 (2026-10-15)

원인은 긴 도시 기록을 매번 처음부터 재생하는 복원 방식, 통합 화면에 빠져 있던 그리기 횟수 제한, 숨겨진 이름표의 반복 배치, 매 차로마다 전체 차량을 검색하는 계산이었다. 현재 상태를 IndexedDB에 저장하고, 호환되는 상태에서는 즉시 이어 간다. 이전 기록/JSON의 첫 계산은 Worker에서 수행한다. 중단·오류 때 원본 기록은 보존한다.

같은 PC의 Chrome, 개발 서버 전체 통합 UI, 시드 2404, 정책 없는 도시 시간 900초, 1440×1000, 보통 품질/4배속에서 측정했다. CPU 감속은 적용하지 않았다. 각 지도에서 5초간 CDP 메인 스레드 작업과 레이아웃 시간을 읽었다.

| 항목 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 기존 15분 기록 최초 복원 | 8.73초 | 7.58초 |
| 저장 후 다시 열기 | 8.54초 | 1.95초 |
| 일반 지도 메인 스레드 작업 / 5초 | 4,879ms | 2,949ms |
| 수질 지도 메인 스레드 작업 / 5초 | 5,006ms | 3,376ms |
| 수질 지도 레이아웃 횟수 / 5초 | 3,045회 | 235회 |
| 수질 지도 레이아웃 시간 / 5초 | 290ms | 37ms |

재진입 시간은 페이지 이동부터 도시가 입력 가능한 상태까지다. 수정 후 재진입은 상태 캐시를 사용하며, 최초 복원은 같은 기존 명령 기록을 모두 계산하는 조건이다. 최초 변환 자체가 즉시 끝나지는 않는다. 메인 스레드 작업은 약 33~40% 감소했지만 전체 시스템 CPU나 GPU 사용률을 뜻하지 않는다. RAF 콜백 수는 디스플레이 주사율에 따른 값으로, 3D 그리기 횟수/FPS와 다르다. 통합 3D는 보통 60/가볍게 30회로 제한한다.

별도 Node 측정에서 도시 30분 기록의 전체 재생은 21.01→14.53초, 같은 상태의 체크포인트 생성은 20.6ms, 복원은 77.0ms였다. 이 값은 브라우저 다운로드·초기 3D 구성 시간을 포함하지 않는다. 차량/대기/물질 묶음 수는 이전과 동일했다. 수정 전 엔진 측정에는 CPU 프로파일러와 브라우저 측정이 함께 실행되었으므로 순수 엔진 속도비를 엄밀한 벤치마크로 해석하지 않는다.

```powershell
node --import tsx tests/live-performance.ts after
$env:PERF_LABEL='after'
npm run test:browser -- tests/e2e/live-performance.spec.ts
```

원자료는 `output/live-engine-before.json`, `live-engine-after.json`, `live-ui-before.json`, `live-ui-after.json`. 장치와 백그라운드 부하에 따라 달라지는 단일 관측이며 학교 PC 실측은 아니다. 화면 제한·캐시는 계산 수요나 정책 효과를 바꾸지 않는다. 배포 모드와 저장 중단/재시도/Worker 제한은 별도 기능 검사로 확인한다.

## 면적 4배 지도 재측정 (2026-10-14)

`river-districts-v2`에서 신호등 전구를 하나의 InstancedMesh로 합치고 보행 경로를 출발점별로 재사용했다. Chrome CPU 4배 감속, 기존 독립 렌더러 측정 장면에서 다음을 확인했다. 실제 학교 GPU나 전체 제품 HUD의 측정은 아니다.

| 장면 | 일반 화면 | 가벼운 화면 | draw calls |
| --- | ---: | ---: | ---: |
| 시설 계획 · 접근성 이름표 12개 | 35.7 FPS | 30.0 FPS | 293 |
| 물류 · 화물차 3대 | 24.5 FPS | 29.8 FPS | 312 |

결과는 `output/facility-performance.json`, `output/logistics-performance.json`에 저장했다. 아래 이전 지도 측정과 구분한다.

도움말 `?` → **화면이 느릴 때**를 펼쳐 화면 품질을 선택한다. 새 정보창이나 항상 보이는 성능 계기판은 추가하지 않았다.

| 설정                | 보통      | 가볍게 |
| ------------------- | --------- | ------ |
| 3D 해상도 배율 상한 | 1.5       | 1      |
| 그림자              | 2048px 맵 | 끔     |
| 그리기 빈도 상한    | 60FPS     | 30FPS  |
| HTML 글자·버튼      | 동일      | 동일   |
| 교통 계산·수요·정책 | 동일      | 동일   |

고해상도 화면에서는 3D 캔버스의 프레임당 픽셀 수가 보통의 약 44%가 된다. 화면 주사율과 실제 부하에 따라 표시 빈도는 달라진다. 품질 전환 시 실험을 초기화하지 않고, 같은 시드와 관찰 종료 시각에서 결과도 같다. localStorage에 선택을 기억하며 저장 접근을 막은 브라우저에서도 현재 선택은 적용한다. WebGL 안티앨리어싱은 두 모드 모두 유지한다.

`RenderClock`은 다음 그리기 시각을 누적한다. 144Hz처럼 60으로 나누어떨어지지 않는 화면에서도 시간을 버리지 않아 60/30FPS의 평균 빈도를 유지한다. 긴 중단 뒤에는 누락한 그리기를 한꺼번에 실행하지 않는다. 교통 엔진의 0.1초 고정 계산은 프레임 제한과 분리되어 있다.

## 초기 로딩

HTML에 도시 준비 안내를 넣고, CSS와 작은 초기 JS가 먼저 열린다. 게임 모듈과 Three.js 청크를 이어서 불러오며 실패하면 다시 열기 버튼을 제공한다. 라이브러리 청크를 별도 캐시할 수 있다. [Vite의 분할 설정](https://vite.dev/guide/build.html#chunking-strategy)을 사용한다.

| 배포 파일 |     원본 |     gzip |
| --------- | -------: | -------: |
| 초기 JS   |   2.78KB |   1.43KB |
| 게임 코드 | 232.01KB |  72.94KB |
| Three.js  | 497.20KB | 124.99KB |
| CSS       |  37.98KB |   9.10KB |

전체 JS는 약 732KB이며 게임 실행에는 세 청크가 모두 필요하다. 주민 말풍선·정책 표시·건물 색 지도·보행 범위·물류 시나리오를 포함한 빌드 크기다. 500KB를 넘는 단일 청크 경고는 사라졌다. 압축 전송 여부는 정적 서버 설정에 따른다. 다운로드 속도 자체의 개선이나 첫 실행 시간 단축을 실측한 수치는 아니다.

## 재현 방법

```powershell
npm ci
npm run verify:performance
```

설치된 Google Chrome을 사용하며 5174의 개발 서버를 재사용하거나 시작한다. 같은 `CityRenderer`와 `TrafficSimulation`을 불러오는 별도 측정 페이지에서 교통 12조건과 수거 2조건, 시설 계획 2조건, 개발·환경 2조건과 물류 2조건을 한 번에 하나씩 실행한다. 결과는 `output/performance.json`, `output/waste-performance.json`, `output/facility-performance.json`, `output/environment-performance.json`, `output/logistics-performance.json`에 쓴다. 측정 페이지와 검사 객체는 배포 파일에 들어가지 않는다.

- 수요 80·150·300건 × 보통/가볍게 × CPU 감속 없음/4배. 실제 도로 위 차량 수는 별도 기록한다.
- 보행자 60명 고정 수요를 포함하며 실제 활성 보행자 수와 통계도 별도 기록한다.
- 시드 2404, 세 정책 조합, 180초까지 계산한 동일 초기 상태, 2배속 진행.
- 고정 카메라, 화면 1280×720 CSS 픽셀, 기기 배율 1.5. 렌더 준비 1.5초 뒤 5초 측정.
- FPS는 초당 그리기 호출 수, p95는 호출 간격의 95백분위다. 실제 디스플레이의 표시 완료나 GPU 타이머 수치는 아니다.
- 렌더 CPU는 그리기 호출의 동기 실행 시간, 엔진 CPU는 진행·주기적 통계 계산 시간이다. 비동기 GPU 실행 시간은 포함하지 않는다.
- CPU 4배 감속은 Chrome 모의 조건이다. GPU는 같은 실제 장치를 사용한다. 생산 빌드의 전체 HUD, 카메라 이동, 차가운 시작, 8배속은 이 측정에 포함하지 않는다.
- 실행 PC·GPU·브라우저·동시 작업에 따라 달라지는 짧은 관측이다. 보편적인 FPS 통과선을 테스트에 강제하지 않는다.

실제 학교 PC에서는 다른 작업을 줄인 상태로 이 명령을 실행해 파일을 보관한다. 이어서 전체 앱에서 보통/가볍게, 혼잡도, 카메라 조작, 8배속 및 정책 비교를 직접 확인한다. 실제 학교 iGPU 장치에서의 측정과 학생의 글자 크기·움직임 평가는 아직 남아 있다.

배포 파일 검증은 별도로 실행한다.

```powershell
npm run build
npm run verify:production
```

포트 5176에서 dist를 잠시 제공해 초기 안내, 로딩 실패 후 재시도, 가벼운 화면의 기본/신호 실험과 쓰레기차 추가 실험, 시설 확장·출입로 계획과 산업 확장·완충 실험, 엔진과 동일한 JSON 저장과 개발용 검사 객체 제외를 확인한다. 종료 시 서버와 브라우저를 닫는다.
